# Підтримка Text Work

## Швидка перевірка змін підсвітки

1. Відкрийте `test.txt` у VS Code в режимі `text-work`.
2. Додайте приклади нового слова в нижньому, верхньому та змішаному регістрі, якщо
   правило не залежить від регістру.
3. Перевірте, що нове правило не перефарбувало випадкові частини інших слів.
4. Перевірте поруч числа, лапки, URL, `@tags` і списки: ці загальні правила можуть
   перетинатися з новим правилом.

## Автоматична перевірка логіки списків

Виконайте `npm test`. Тести перевіряють розбір пунктів і продовження числових,
літерних, римських та маркованих списків, включно з переходом `z.` → `aa.`.

## Перевірка дій зі списками

У файлі `test.txt` перевірте:

- `Enter` після `*`, `-`, `•`, `1.`, `a.` та `i.`;
- `Enter` на порожньому пункті — пункт повинен прибратися;
- вставлення пункту всередині числового списку — наступні пункти того самого рівня
  повинні перенумеруватися;
- `Tab` і `Shift+Tab` для вкладеного пункту;
- числові, літерні та римські послідовності;
- `Alt+Enter` і `Shift+Alt+Enter` для розділювача з датою.

## Збірка та публікація

У `package.json` зберігається версія розширення. Збірка виконується командою
`vsce package`, яка створює файл `.vsix` у корені проєкту.

Поточні GitHub Actions автоматично збирають проєкт:

- гілка `dev` створює prerelease;
- гілка `main` публікує версію у Visual Studio Marketplace і створює GitHub Release.

Перед релізом варто звірити номер версії, `CHANGELOG.md`, працездатність ручних
сценаріїв вище та відповідність імені згенерованого `.vsix` версії в `package.json`.

## Відомі застарілі допоміжні команди

`scripts/update-extension.sh` і `scripts/commands.txt` містять застарілі
ідентифікатор видавця або номер версії пакета. Не використовуйте їх як є для
поточної версії без перевірки `package.json` та фактичного імені `.vsix`.
